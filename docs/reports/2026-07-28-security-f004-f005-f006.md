## F-006 — Cookie `Max-Age` integer overflow (VENDORED odin-http)

**Severity: LOW for Uruquim (code path unreachable); MEDIUM-HIGH if a future
Uruquim cookie API is exposed, or for direct consumers of the vendored
backend.** CWE-20 / CWE-190 (Integer Overflow). Same family as F-001 —
`strconv.parse_int` without range check. **Report upstream (laytan/odin-http).**

### Reachability caveat (correction during write-up)

**This parser is NOT reachable through the current Uruquim framework.**
`web/` has no cookie API by design — `web/secure.odin:42` states "Uruquim
sets no cookies and has no cookie API". `request_cookies`,
`request_cookies_iter`, and `request_cookie_get` exist only inside
`vendor/odin-http` and are not called from any Uruquim `web/*` entry point.
An attacker who can only reach Uruquim's public surface cannot drive
`Max-Age` through this parser. Reported anyway because (a) it is the F-001
bug class and the fix is trivial, (b) the live target in this session
silently accepted arbitrary `Cookie:` headers and there was no observable
crash for the same reason — the parser never runs — which is itself a
useful thing to know when judging earlier fuzz output, and (c) any
application that links the vendored backend directly, or a future Uruquim
cookie reader, exposes it immediately.

### Affected code

`vendor/odin-http/cookie.odin`:

- **Line 148** — `Max-Age` attribute:
  `cookie.max_age_secs = strconv.parse_int(value, 10) or_return`
- **Lines 334-345** — date year:
  `parse_digits(token, 2, 4, true)` → year fed to
  `time.datetime_to_time(year, ...)` with no upper bound.

### Root cause

`strconv.parse_int(str, 10)` on this pinned toolchain (dev-2026-07-nightly:
819fdc7) does not range-check: an oversized decimal literal wraps modulo
2^64 and returns `ok = true` with whatever value the wrap produced. This is
exactly the behavior that drove F-001 (negative chunk-size). The cookie
parser calls it directly on attacker-controlled `Max-Age`:

```odin
// vendor/odin-http/cookie.odin:148
cookie.max_age_secs = strconv.parse_int(value, 10) or_return
```

A cookie header of:

```
Cookie: session=abc; Max-Age=99999999999999999999999999999999
```

yields a wrapped, possibly negative `max_age_secs` that the rest of the
framework then treats as a legitimate attribute. The semantic effect depends
on the application's downstream use (cache control, session lifetime
arithmetic, set-cookie re-emission), but the parser is contractually bound
to either accept a valid lifetime or reject — not to silently hand a wrapped
integer to the caller.

The date-parsing companion (year up to 9999 → `time.datetime_to_time`)
compounds it: an absurd `Expires=Fri, 99 Jan 99999 99:99:99 GMT` head also
feeds attacker-controlled magnitude into `time` without a sanity check.

### Trigger (unauthenticated, **upstream consumers only**)

**Through Uruquim: not reachable.** Through a direct consumer of the
vendored `odin-http` server (or a future Uruquim cookie API): any handler
that reads `Cookie:` via `request_cookies`/`request_cookie_get` on an
endpoint reachable without authentication. No body required.

```
GET / HTTP/1.1
Host: x
Cookie: a=b; Max-Age=99999999999999999999999999999999
```

### Verification

Static — confirmed against `vendor/odin-http/cookie.odin` at the lines
above, with the `strconv.parse_int` wrap behavior already proven in F-001
(`ffffffffffffffff` → -1 in hex; the same holds for decimal overflow).
Not fuzzed live because the lab target's cookie-consuming handlers aren't
wired to an attack surface yet — this is a parser-level call-out, not a
crash PoC.

### Fix (suggested for upstream)

Reject at the parse site, exactly as F-001 recommended for chunk sizes:

```odin
v, ok := strconv.parse_int(value, 10)
if !ok || v < 0 || v > MAX_REASONABLE_MAX_AGE {
    // skip the attribute (or fail the parse)
}
cookie.max_age_secs = v
```

For the year path in `cookie_date_parse`, enforce `1990 <= year <= 9999`
before `time.datetime_to_time`, or treat an out-of-range year as a parse
error and skip the `Expires` attribute (the cookie is still valid without
it). Both rejections are RFC-conformant: RFC 6265 §5.2.2 says a failed
`Max-Age` should be ignored, and §5.1.1 requires a sensible date range.

## F-005 — Silent connection drop on oversized header block (VENDORED odin-http)

**Severity: LOW-MEDIUM (availability / protocol correctness). CWE-400
(Uncontrolled Resource Consumption) ambiguous handling.**
**Upstream issue candidate.**

### Affected code

`vendor/odin-http/server.odin` (header-line accounting) interacting with
`vendor/odin-http/scanner.odin` (buffer growth).

### Observed behavior (live, this session)

With `limit_headers = 8000` (the configured default), the lab target was
sent single-header requests of varying total size:

| Header block size | Response |
|-------------------|----------|
| 7,932 bytes | `200 OK` |
| 8,032 bytes | `431 Request Header Fields Too Large` ✓ expected |
| 8,132 bytes | `431` ✓ |
| **8,532 bytes** | **connection closed silently, no response, no log** |
| **9,032 bytes** | **connection closed silently** |

The first two over-limit responses are correct. Past some threshold above
~8.1 KiB, the server stops emitting the 431 and instead drops the
connection: the FB/HTTP client sees an empty response, the server log is
empty (the `log.warn("request headers too large")` at `server.odin:1575`
never fires), and an ASan build of the same target produces zero output.

### Root-cause hypothesis (not yet triaged in gdb)

The 431 path runs only when a parsed header line causes the budget to dip
to `<= 0` (server.odin:1573-1574). For a single very large header, the loop
never sees a *complete* token until the buffer holds the whole line; growth
of that buffer is governed by `scanner.odin:224-253`.

The buffer-doubling check `s.end - s.start >= s.max_token_size` (scanner:229)
compares against the *byte budget* — for a single 9 KiB header with budget
8,000, the check fires only when the buffer is full and tries to grow past
8,192 bytes. By that point `s.end - s.start` has already crossed the budget
for a while, but it only trips `.Too_Long` on the *next* grow attempt, and
the error is then surfaced via `callback(..., .Too_Long)`. The callback in
`on_header_line` (server.odin:1553-1558) does:

```odin
if err != nil {
    log.warnf("request scanning error: %v", err)
    clean_request_loop(l.conn, close = true)
    return
}
```

It logs and closes — but the log was absent in our runs. Either the error
path runs but `log.warnf` is suppressed at the effective log level, or the
close path runs *before* the error is ever delivered (the kernel RST from
the client's `shutdown(SHUT_WR)` landing in the same tick). Either way the
client receives *no status code*.

### Impact

- A client cannot distinguish "server isn't there" from "request too
  large" — monitoring and retry logic misfires.
- A scanner `.Too_Long` that should turn into 431 instead becomes a
  silent close in some size regime. Not a memory bug; a correctness/UX
  issue with availability flavor.
- The exact threshold (~8.1 KiB → ~8.5 KiB) is murky: it depends on the
  request-line size and on buffer growth step boundaries, which makes it a
  poor thing for clients to rely on.

### Repro

Lab target on `127.0.0.1:18080`:

```python
import socket
v = b"D" * 8500
p = b"GET / HTTP/1.1\r\nHost: x\r\nX: " + v + b"\r\n\r\n"
s = socket.create_connection(("127.0.0.1", 18080))
s.sendall(p); s.shutdown(socket.SHUT_WR)
out = b""
while True:
    d = s.recv(4096)
    if not d: break
    out += d
print(out)   # b''
```

### Recommendations

1. Convert scanner `.Too_Long` in the header-reading phase into an explicit
   `431` response before closing, not a log line + close. The limit is
   configured; the status code should be deterministic.
2. Log at the dispatched status (one line, not one per header), so the
   incident is visible.
3. Document the current effective cap (incl. request-line budget that
   deducts from the same atom) so operators aren't surprised by a ~1 %
   shortfall of "8000".

## F-004 — Stream pump holds zero-copy ring slice across async send (URUQUIM)

**Severity: HIGH if triggered. CWE-416-adjacent (lifetime).**
**STATUS: REVIEWED, NOT REPRODUCED.** Reported as a design concern with the
specific guard that appears to save it. Flagged for upstream review of the
WP90b pump, not as a live exploit.

### Affected code

`web/internal/transport/odin_http_adapter.odin`:

- `stream_pump_run` (lines ~815-849): holds a slice of the slot's ring
  buffer across `nbio.send_poly`.
- `stream_conn_torn_down` (line 762-775): on backend teardown, calls
  `stream.close` + `stream.retire`, returning the slot to the free list.
- `web/internal/stream/stream.odin` `store`: kept for reuse across slots
  (line ~229), so a retired slot's bytes are not unmapped — a new stream on
  the slot writes into the same buffer at the same offsets.

### The suspect interleaving

1. Pump: `data := s.store[e.offset : e.offset + e.len]` — zero-copy slice
   into the ring.
2. Pump issues async `nbio.send_poly({prefix, data, CRLF})`.
3. **Race**: kernel-side completion of the send has not yet fired; the
   data is queued in io_uring but not yet on the wire.
4. Client RST: backend runs `connection_teardown → stream_conn_torn_down`
   → `stream.close + stream.retire`.
5. A *new* stream is opened, the allocator pops the same slot, its
   producer does `try_send` → `store_reserve + copy` into the same
   offsets the still-in-flight send references.
6. The kernel eventually writes the iovec contents — which now contain the
   new stream's data, not the old stream's.

The expected outcome if triggered: cross-stream data bleed (chunks of one
client's stream appearing inside another client's HTTP response), or, under
ASan, a `heap-use-after-free` if the ring's storage were also released —
it is not, which makes this UAF-adjacent (lifetime-violating reuse rather
than freed-memory access).

### Why the harness did not fire it

Wrote `/tmp/attacklab/poc_f004.py` — burst of 8 `/big` streams (2 chunks
× 128 KiB each), each RST'd with `SO_LINGER {1,0}` after reading only the
headers, followed by 4 clean `/big` streams to force slot reuse. Ran
600 rounds × 12 streams = ~7,200 stream activations against an ASan-built
target. **No crash, no ASan event, log file empty, server stayed up the
whole time.**

Three guards in the current code plausibly prevent the trigger:

1. **`link.terminated` is set FIRST** in `stream_conn_torn_down` (line 766)
   *before* `stream.close` and `stream.retire`. `stream_pump_run` (line 809)
   checks `link.terminated || conn.state >= .Closing` at the top and
   refuses to schedule any further send. The pump therefore doesn't re-arm
   after teardown begins.
2. **`conn.pending_send` interlock.** A second `stream_pump_run` refuses
   while `conn.pending_send != nil`, so even if the completion callback
   races teardown it cannot start a new send. The in-flight one is left
   to the backend's own `nbio.remove` in the connection close path.
3. **The ring buffer is retained across slots** (`registry_init` keeps one
   `store` for the registry's lifetime), so even if a late completion did
   fire, it would hit *live* memory that the registry still owns — which
   is why ASan stays silent even over thousands of RSTs. This converts
   "freed memory" into "data-race on a live buffer", which is harder to
   observe in a black-box harness.

### Why this is still worth flagging

- The owner-lock comment (`stream.odin:96`) claims *"reusing the slot
  before the owner is done would let a new stream overwrite bytes mid-send"*
  — exactly the F-004 mechanism. The current defense is *implicit* (the
  three guards above), not a documented invariant.
- Guard 1 depends on `conn.state >= .Closing` transitioning *before*
  `stream_conn_torn_down` is called. If an external code path (deadline
  sweep, shutdown force-close, scanner error) ever retires the slot
  *without* flipping `conn.state` or `link.terminated` first, the pump
  could schedule a new send against a recycled slot.
- Guard 2 only blocks *new* sends. The send already in flight when the
  RST lands has its slice taken before the RST; if `nbio.remove` does not
  block until the kernel drops the iovec reference, the window between
  "slot retired" and "kernel done with the buffer" remains. On Linux the
  io_uring documentation does not make that guarantee strongly.

### Recommendations

1. **Add an explicit invariant** in `stream_conn_torn_down`: while an
   `nbio.send_poly` op is outstanding and references a slot's ring, that
   slot's `retire` must wait. Either:
   - Delay `stream.retire` until the tracked `pending_send` completion
     fires (add a slot-level `send_in_flight` refcount); or
   - Have the *completion callback itself* (`on_stream_chunk_sent` /
     `on_stream_terminator_sent`) perform `retire` on the error path
     instead of `stream_teardown_error` doing it directly.
2. **Add a regression test** that drives the RST race under ASan with the
   slot cap tuned to `1` and a producer that always has a large chunk
   ready, so a reuse-of-slot *must* happen during the in-flight window. A
   harness of ~7,200 RST'd streams in this session did not trigger it, so
   the test should force the window wider — e.g. by injecting a controlled
   delay in the kernel-side send path or by using a chunk sized to ride
   multiple io_uring submissions.
3. **Document the io_uring buffer-lifetime contract** in the WP90b pump
   spec section: which side of `nbio.remove` guarantees the kernel will not
   read the iovec bytes after return. If that guarantee is weaker than the
   current code assumes, the pump needs to copy the data into an
   adapter-owned buffer for the duration of the send.
4. Mark this report as **F-004-REVIEWED, exploit not constructed**. It is
   *not* a proven finding; it is a flag on the WP90b pump's lifetime
   contract for the next reviewer.

## F-007 — Spool admission slot leak on `begin` failure (URUQUIM, Phase 7.5-C2)

**Severity: LOW (latent). CWE-772 (Missing Release of Resource after
Effective Lifetime).** Confirmed by code trace; **not remote-triggerable**
in any normal configuration because triggering `begin` failure requires
disk-full or fd-exhaustion on the spool directory, both of which an
operator notices before the leak becomes observable.

### Affected code

`web/internal/ingest/ingest.odin` + `web/internal/transport/odin_http_adapter.odin`:

- `admit` (`ingest.odin:105-123`): on success, increments
  `a.active` under the admission mutex and returns `.Ready`.
- `start_upload` (`odin_http_adapter.odin:538-541`): if `ingest.begin` fails,
  calls `upload_refuse(exchange, .Insufficient_Storage)` and returns.
- `upload_refuse` (`odin_http_adapter.odin:594-598`): only sets `connection:
  close` and writes the status. **It does not call `ingest.cancel` and does
  not decrement `a.active`.**

```odin
// odin_http_adapter.odin:538
if ingest.begin(&runtime.admission, &exchange.spool) != .Ready {
    upload_refuse(exchange, http.Status.Insufficient_Storage)
    return
}
```

`begin` itself does not unwind the `admit` reservation inside its failure
path — `begin` returns `.Disk_Full` without touching `a.active`
(`ingest.odin:139-163`); the `os.open` failure branch only does
`delete(path)` and returns.

### Effect

Every `begin` failure permanently consumes one `a.active` slot. Once
`a.active >= cfg.max_concurrent`, all subsequent large-body uploads are
refused with `.Refused_Admission` (`503`). No reset path exists short of
server restart; the matching `a.process_bytes` is unaffected (`begin`
never reserved bytes), so this is a pure slot-accounting leak.

### Reachability

- **Not remote-triggerable** in normal operation: `begin` can only fail on
  `os.open` errors, which means the operator-designated spool directory is
  out of inodes, out of space, has the wrong permissions, or the process
  is out of file descriptors. The first three are operator-visible long
  before an attacker can fill them; the last one (`EMFILE`) requires the
  attacker to also exhaust fds, which is bounded by `max_connections` and
  would already produce other symptoms.
- **Real bug**: the `start_upload` comment at line 535 explicitly claims
  "On failure the admission slot is released the same way the multipart
  consumer releases it (`mp_start_content`)". This is false in the current
  code — `mp_start_content`'s failure path calls `ingest.cancel` (see
  `web/internal/ingest/multipart.odin`), but the raw-upload path does not.

### Fix (one line)

In `start_upload` (`odin_http_adapter.odin:538-541`), call `ingest.cancel`
on the same zero-value-but-admitted spool to release the slot, or add an
`ingest.release_admission` helper that skips the file/path cleanup:

```odin
if ingest.begin(&runtime.admission, &exchange.spool) != .Ready {
    // begin failed before it owned anything; release the slot admit took.
    a := &runtime.admission
    sync.mutex_lock(&a.mu)
    if a.active > 0 { a.active -= 1 }
    sync.mutex_unlock(&a.mu)
    upload_refuse(exchange, http.Status.Insufficient_Storage)
    return
}
```

A cleaner shape is to give `ingest` a `release_admission(a: ^Admission)`
public so the decrement stays beside the increment; optics aside, refusing
without releasing is the bug regardless of which side owns the counter.

### Live-test note

I could not construct a remote trigger for `begin` failure without
simulating disk-full on `/tmp/attacklab/spooldir`, which would hurt the
host. The leak was confirmed by tracing every callsite of `admit` (one),
every decrement site of `a.active` (`ingest.cancel` and `ingest.persist`,
both gated on a *successful* `begin`), and the absence of a `cancel` call
between `begin != .Ready` and `upload_refuse`. The test in this session
(2× RST mid-spool under `max_concurrent = 2`, followed by 3 sequential
spooled uploads) proved the RST path correctly releases the slot via
`on_upload_done(.Failed) → ingest.cancel`; the `begin` path is the only
one that leaks.

## Methodology notes / non-findings

Things that were beaten on and held:

- **Header duplicate-name merge** (`http.odin:222`): the `strings.concatenate
  ({old, ", ", new}, allocator)` on every duplicate header is real, but
  measured timing grows linearly with header count, not quadratically — the
  `len+4` builder and map overhead dominate, so the merge amortizes.
  Sub-linear constant factor. Not a finding.
- **Stream registry token/generation** (`stream.odin`): u64 generation never
  resets on reuse, equality check under slot mutex, slot bounds checked at
  every entry. Reviewed, clean.
- **Ring bounds + budget accounting** (`stream.odin:280-345`): `store_reserve`
  before copy, in-flight oldest event stays counted in `store_used` until
  `complete_event`, `atomic_add` + compare-then-rollback on `total_bytes`.
  No modular wrap, no double-release. Reviewed, clean.
- **WP92 backpressure refusal paths**: every decrement paired with the
  matching increment on every refusal branch (reviewer C traced all of
  them). Liveness edge F-SUSP-1 is a bounded event-drop on an
  already-dying stream, not exploitable.

Surfaces *not* re-examined this round: chunked decoder (F-001 fixed
upstream), multipart (clean in 8,000 iters on 2026-07-23), JSON path
tracking, `body_url_encoded` unbounded pair count, static-file serving
`lstat` walk. Those are the next most promising parser fuzz targets,
carried over to the follow-up list in `/home/jp/next-fuzz-targets.md`.
