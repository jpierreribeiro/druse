## 1. O que é o Druse

Um **microframework web em Odin** para APIs JSON, escrito com **0% de código
humano** — construído inteiramente por agentes de IA sob supervisão do dono.

**Três compromissos declarados:** simples por padrão, explícito quando preciso,
orientado a dados por baixo.

**A decisão de arquitetura que mais define o projeto:** o core **não cresce por
plugin**. Capacidade opcional vive num repositório separado
([druse-crystals](https://github.com/jpierreribeiro/druse-crystals)) como pacotes
Odin comuns — PostgreSQL, validação, HTTP de saída, métricas. Não há registro,
hook de descoberta, ABI dinâmica nem contêiner de extensão. **O que você não
importa não te custa nada, e o core não pode crescer por porta lateral.**

**Escala:** `web/` tem ~15.500 linhas em 48 arquivos. 122 suítes de teste.

## 2. Como funciona — o fluxo de uma requisição

```
   cliente
     │
     ▼
  [ Caddy fixado ]  ← TLS; é a ÚNICA borda suportada (docs/supported-profile.md)
     │
     ▼
  [ transporte ]  vendor/odin-http + vendor/nbio  → io_uring no Linux
     │              web/internal/transport
     │
     ├─ acceptor dedicado aceita a conexão
     │     └─ se TODAS as lanes estão ocupadas: fecha o socket SEM resposta HTTP
     │        e incrementa `saturation_refusals`  ← isto é "recusa de saturação"
     │
     ▼
  [ lane de handler ]  concorrência = `Limits.max_handlers`
     │                  0 (default) → clamp(núcleos físicos, 4, 32)
     │
     ▼
  [ router ]  web/router.odin, dispatch_table/dispatch_match/dispatch_index
     │
     ▼
  [ middleware ]  composição explícita, curto-circuito explícito
     │
     ▼
  [ handler ]  síncrono do ponto de vista da aplicação
     │           recebe ^web.Context; um único estado tipado da aplicação
     │
     ▼
  [ extractors ]  parse que falha em resposta de erro TIPADA
     │             web/extract.odin, json_decode.odin, multipart.odin, upload.odin
     │
     ▼
  [ resposta ]  contrato COMMIT-ONCE: web.ok / text / bytes / stream
                web/respond.odin, response.odin, stream.odin
```

### Conceitos que você precisa entender antes de mexer

**Lane ≠ worker de CPU.** Uma lane é um *slot de concorrência*. Uma lane
bloqueada dentro de um handler **não consome CPU** — ela segura o slot.
Dimensionar lanes por núcleo é o erro que travou um work package por dois dias
(§6.1). Se sua aplicação tem qualquer handler que espera (banco, upstream,
`sleep`), **menos lanes que o default é a decisão que mais dói**.

**Recusa de saturação não é 503.** É **conexão fechada sem resposta HTTP**. O
cliente vê fim de conexão, não um status. E ela é função de **duas** variáveis
medidas separadamente: a **rajada de reconexão** e a **taxa**.

**Commit-once.** Uma resposta é comprometida uma vez. O contrato é o mesmo para
JSON, texto, bytes e stream.

**Memória:** arena por requisição (`web/request_arena.odin`). A aplicação **não
pode reter** slices, strings, headers ou views de corpo além do ciclo da
requisição sem copiar explicitamente.

**Observabilidade:** `web/observability.odin` + `observer.odin`. Há um canal de
snapshot **fora de banda** (ADR-050) — um arquivo que o servidor escreve de uma
thread que **não possui lane nenhuma**, justamente porque `/stats` como rota
comum se perde sob saturação (medido: 111 de 8.611 coletas perdidas em 12 h).

## 3. Onde o projeto está

### 3.1 O programa de prontidão

Três portões: **R1** (piloto controlado) → **R2** (produção restrita) → **R3**
(maturidade geral). **Está em R1 desde 2026-08-02 e continua lá.**

**A confusão mais comum:** muito trabalho acontece e o portão não anda. **É o
desenho funcionando.** O programa recusa explicitamente "existe um teste",
"funcionou na máquina do autor" e "o resultado histórico é parecido" como
estados de encerramento.

### 3.2 As seis regras globais (leia antes de mudar qualquer coisa)

| | regra |
|---|---|
| **G1** | mudar código, toolchain **ou configuração load-bearing** cria **candidato novo** — a escada de testes reinicia do zero |
| **G2** | todo instrumento prova a si mesmo **antes** de medir: controle positivo que fica verde **e mutante que fica vermelho pela razão esperada** |
| **G3** | critérios congelados **antes** do run; emenda depois de ver o resultado invalida o run |
| **G5** | um plano pode nomear uma necessidade, **não inventar assinatura de API** |

**Essas regras são o produto tanto quanto o código.** Elas são a razão de o
projeto ter encontrado defeitos reais em vez de acumular confiança falsa.

### 3.3 R2 — oito peças

## 4. O que está medido — e vale citar

Tudo abaixo tem artefato com hash em `evidence/`.

**Estabilidade (Final 1, 12 h):** 334 ciclos, **zero erro de transporte** no
`/health`, p99 mediano **1.165 µs**, RSS crescendo **0,99 KiB/h** contra teto de
1 MiB/h — e a inclinação foi **avaliada**, não passou por falta de dado.

**Capacidade:** **não há knee até 10.000 req/s** em dois núcleos físicos.
Goodput ≥ 99,99%, p99 de 1,27 ms a 1,79 ms ao longo de um fator de dez na carga.
Degradação suave.

**Região segura publicada** (`docs/safe-operating-region.md`): verde até
~2.500/s, amarela até 7.000, laranja até 10.000, desconhecida acima.

**Efeito de `max_handlers`, medido:**

| config | p99 a 960 req/s | recusas a 5.000 req/s |
|---|---:|---:|
| 1 lane | **34.174 µs** | 0 |
| 2 lanes | 1.250 µs | **214** |
| **4 (default)** | 1.257 µs | **1** |
| 8 lanes | 1.254 µs | 0 |

**Integridade de release:** hash do artefato implantado provado igual ao
aprovado, **com mutante**. Releases são **verificados por hash e NÃO assinados**,
e a política proíbe a palavra "assinado" enquanto valer
(`docs/release-integrity-policy.md`).

## 5. O que NÃO está medido — a lista que mais importa

1. **Nenhum tráfego real. Nunca.** Os degraus 2–6 do canário são risco aceito
   assinado. Tudo que existe é carga sintética de um gerador do próprio projeto.
2. **Recuperação depois de sobrecarga não foi medida.** Sabemos o caminho de ida
   até 10.000 req/s, não o de volta. **É a maior lacuna da região segura.**
3. **SLO por workload: 15 de 18 células de latência em aberto** — e agora se sabe
   por quê (§6.4).
4. **Uma classe de máquina, um mix.** `c5.2xlarge`, dois núcleos para o servidor,
   **um** handler bloqueante a 1–2 req/s. O que generaliza é o **mecanismo**, não
   os números.
5. **Falha de handler ainda custa o processo.** O conserto é a Fase 2 do R3
   (processos worker), não feito.
6. **Sem comparação com pares** (proibida sem harness que prove trabalho
   equivalente) e **sem custo de TLS isolado**.

## 6. Problemas encontrados

### 6.1 RESOLVIDO — a campanha media a configuração errada

O R2-WP04 parou por dois dias descendo a taxa três vezes (f=0,15 → 0,10 → 0,06)
fugindo de recusas, e o piso não se movia.

**Causa:** a campanha fixara `max_handlers = 2`, **abaixo do piso do default do
produto** (4). O raciocínio escrito no pré-registro — *"dois núcleos físicos não
hospedam quatro lanes"* — **está medido como errado**.

**Correção:** parar de sobrepor o default. A escada pré-final passou inteira,
**zero recusa de carga em 80 ciclos**, sem uma linha de código mudar.

### 6.2 ABERTO E BLOQUEANTE — três hosts mortos sob carga

| data | host | quando | sintoma |
|---|---|---|---|
| 2026-08-04 | `184.72.201.140` | sob carga | `sshd` travado; kernel trocado por auto-upgrade |
| 2026-08-04 | `3.208.73.168` | sob carga | sumiu da rede |
| 2026-08-06 | `98.92.141.100` | **1h15 dentro do Final 2** | SSH, ICMP e 8080 mudos; não voltou do reboot |

**Nenhum morreu ocioso.** O terceiro tinha auto-upgrade desligado — a causa do
primeiro estava eliminada por construção.

**A pergunta que isso abriu:** *o framework derruba o próprio host?* Se sim, é
**P0 de produção** e o R2 não acontece nem com dois finais verdes.

**Console da AWS do terceiro:** não contém a morte. Mas três linhas do boot
tornam o silêncio informativo:

| linha | consequência |
|---|---|
| `panic=-1` | um panic **reiniciaria na hora** — não houve boot novo |
| `NMI watchdog: permanently disabled` | um *hard lockup* **não imprimiria nada** |
| `nvme_core.io_timeout=4294967295` | I/O de EBS travado **espera para sempre**, sem erro |

**Contrato:** `planning/readiness/HOST-DEATH-preregistration.md` — quatro
hipóteses com critérios congelados antes do dado.

**Três hipóteses já caíram por medição — não as persiga de novo:**

| hipótese | como caiu |
|---|---|
| disco / `BurstBalance` de `gp2` | a campanha usa **~12% da linha de base de IOPS** e 0,08% do teto de vazão. 12% não drena crédito de rajada |
| memória fixada por anéis de io_uring | **`VmPin = 0`** nos dois braços do A/B; anéis = 5, constante |
| RSS crescendo | era **rampa de aquecimento**; cauda do Final 1 = 0,99 KiB/h em 12 h |

### 6.3 ABERTOS, sem causa, não bloqueantes

| ID | o quê |
|---|---|
| **wp123** | `build/check.sh` reprovou uma vez com **507** (`ingest.begin` não abriu o spool); não reproduziu em 41 tentativas. A mensagem de falha **nomeia um defeito que o código não tem mais** — mandou a investigação para o lugar errado, com confiança |
| **ingest-leak** | `server did not start`; **não é lentidão** — 48 medições, pior caso 174 ms contra janela de 600 ms |
| **SHADOW-001** | `web.serve` recebe porta e **nenhum endereço** — não dá para escutar só em loopback. Conter é trabalho do firewall |
| **F8** | limite de memória sob corpo hostil pinado por argumento, não por teste |

**Não "conserte" wp123/ingest-leak alargando janela ou serializando suíte.** Os
dois consertos óbvios escondem a pergunta.

### 6.4 O SLO por workload não pode ser fechado pelo caminho prescrito

Dois problemas independentes, ambos achados em 2026-08-06:

1. **O prazo venceu.** O §6.2 do pré-registro exige o SLO commitado *"before the
   final run"*. **Os dois finais rodaram sem ele.** Um SLO escrito agora não pode
   graduar nenhum dos dois sem ser "G3 lido ao contrário".
2. **A fonte não produz o dado.** O §6.2 manda derivar do knee do WP05, mas o
   harness do knee roda seis geradores separados e depois faz `glob(raw/*.csv)`,
   jogando os seis numa lista só. **Coleta a dimensão por workload e a descarta.**
   Pior: a mistura inclui o `/wait/40ms`, que tem piso de 40 ms por construção —
   o `p999 = 40.249 µs` do ponto K1 **não mede degradação nenhuma**.

**O que existe:** a regra de derivação congelada em commit próprio, antes de
qualquer percentil por workload existir —
`planning/readiness/R2-SLO-derivation-preregistration.md`.

## 8. Indicações de auditoria — onde eu olharia

Ordenado por retorno esperado.

### 8.1 Alta prioridade

1. **`web/internal/transport/` e o uso de io_uring** (`boundary.odin`,
   `odin_http_adapter.odin`; a implementação vem de `vendor/nbio` e
   `vendor/odin-http`). É onde a hipótese H-B
   moraria. Procure: recursos de kernel que crescem por conexão e não são
   liberados; anéis registrados; buffers fixados; descritores. **`VmPin = 0` já
   descarta memória fixada** — olhe slab, `SUnreclaim` e estruturas de socket.
2. **O acceptor e a recusa de saturação.** O contador vive em
   `web/observability.odin`; o caminho que fecha a conexão está em
   `web/internal/transport/boundary.odin` e `odin_http_adapter.odin`. Audite: a
   contabilidade de `saturation_refusals` é exata? Há caminho que feche a conexão
   **sem** incrementar — ou que incremente sem fechar?
3. **A resolução de lanes.** Está em
   `web/internal/transport/odin_http_adapter.odin:34` —
   `resolve_handler_concurrency`, com `AUTO_HANDLER_CONCURRENCY_MIN = 4` e
   `MAX = 32`; o teto de validação `MAX_HANDLER_CONCURRENCY = 256` fica em
   `web/limits.odin:317` e o campo em `web/limits.odin:218`.

   ```odin
   resolve_handler_concurrency :: proc(requested: int) -> int {
       if requested != 0 { return requested }
       return clamp(os.get_processor_core_count(),
                    AUTO_HANDLER_CONCURRENCY_MIN, AUTO_HANDLER_CONCURRENCY_MAX)
   }
   ```

   O default está **medido** como bom. Audite: os extremos (1 lane, 256 lanes);
   se `requested != 0` deveria mesmo aceitar **qualquer** valor sem piso — hoje
   `max_handlers = 1` é aceito e custa p99 de **34 ms**; e se o `clamp` vale em
   todos os caminhos de entrada.
4. **`ingest/` e o spool.** Dois achados abertos (wp123, ingest-leak) apontam
   para lá, e o 507 **colapsa duas causas distintas** que o adapter não
   distingue. Separar as duas causas é trabalho concreto e útil.

### 8.2 Média

5. **Contrato commit-once** (`web/respond.odin`, `response.odin`, `stream.odin`).
   Procure caminho que comprometa duas vezes, ou que comprometa e depois falhe.
6. **`web/client_address.odin`.** Já teve um defeito real (TRUST-001: casamento
   de prefixo sem âncora — escrever `10.0.0.1` confiava em ~110 endereços).
   Corrigido, com 7 testes sobre sockets reais. **Audite a caminhada da cadeia
   `X-Forwarded-For`**, que o mesmo defeito também afetava.
7. **Arena por requisição** (`web/request_arena.odin`). O contrato diz que a
   aplicação não pode reter views. Audite se algum caminho do próprio framework
   retém.
8. **Middleware e curto-circuito** (`web/middleware.odin`). Um middleware que
   curto-circuita sem comprometer resposta deixa a requisição em que estado?

### 8.3 O que NÃO auditar como se fosse produto

Estes são **instrumentos de campanha**, não código de produção — defeitos aqui
custam corridas, não usuários. Mas eles têm histórico:

- `ops/soak/run-soak.sh`, `preflight.sh`, `analyze-soak.py` — três defeitos já
  encontrados e corrigidos, todos da mesma classe: **produzem números confiantes
  e não falham ruidosamente**.

### 8.4 A classe de defeito que este projeto mais produz

**Instrumentos que falham devolvendo um valor plausível em vez de gritar.**
Exemplos reais desta semana:

| comando | disse | era |
|---|---|---|
| `ls .../stats-*.json \| wc -l` | `0` amostras | 34.526 — estourou o `ARG_MAX` |
| `pgrep -f "[s]oak-server"` | servidor morto | vivo há 9h37; o binário é `bin/server` |
| verificação de `MANIFEST.sha256` | `conferem=0` | 15 conferem; o manifesto usa caminho absoluto |
| um monitor de 7 em 7 min | 72 linhas em branco | o host tinha morrido na 12ª |

**Se você escrever qualquer instrumento neste repositório: ele precisa de três
estados, e o terceiro — "não consegui perguntar" — tem de ser barulhento.**

### 8.5 Controles pinados em números envelhecem

**Três controles reprovaram mudanças legítimas em três dias** porque afirmavam um
número em vez de uma propriedade. Se você escrever um controle, **assere a
propriedade** — e prove com mutante.

## 9. Possíveis soluções para o bloqueio atual

| caminho | custo | o que resolve |
|---|---|---|
| **A/B em 2 hosts simultâneos** (recomendado) | 2 máquinas, ~5 h | responde H-A/H-B/H-C de uma vez; amostra **máquina**, que é a variável certa |
| A/B sequencial em 1 host | 1 máquina, ~10 h | mesma resposta, dobro do relógio |
| Trocar volume para `gp3` antes | centavos | fecha H-D formalmente (já implausível pela aritmética) |
| Instrumentar mais contadores de kernel | horas de código | só vale se o A/B apontar direção |

**Se o A/B mostrar que só o Druse mata:** o R2 para, e a investigação vira
engenharia de produto — provavelmente no transporte.

**Se os dois braços morrerem:** é ambiente. Documenta-se como limitação da
campanha, escolhe-se outro tipo de instância, e o R2 segue.

**Se ninguém morrer em ≥ 4 h:** aumenta a duração até reproduzir. O terceiro host
morreu em 1h15, então 4 h já é 3× a margem.

## 11. Avisos práticos

- **Não mexa em `web/` ou `ingest/` enquanto os finais estiverem pendentes.** Sob
  G1 isso cria candidato novo e joga fora as horas já gastas.
- **Não rode `build/check.sh` em paralelo com outra coisa pesada.** Isso produziu
  dois vermelhos falsos, ambos em fixtures que passam sozinhas.
- **`git push` no repo do core às vezes trava.** Contorno conhecido: usar
  `gh api`.
- **O toolchain Odin não é reprodutível.** O `server_sha256` difere a cada build
  da mesma árvore. **Isso está resolvido como evidência**, não como bug: o
  inventário de 559 símbolos (removido o contador interno do compilador) tem o
  **mesmo sha256** nos quatro degraus da escada. Ver
  `evidence/2026-08-05-r2-wp04-default-ladder/CANDIDATE-IDENTITY.md`.
